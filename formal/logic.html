The rules, as logic gates

Each circuit below is a rule Lean proved about the foundry code. Click the inputs on the left to switch them on or off, and follow the orange wires to the output. Every output names the theorem that says it always works this way, for every input, not just the ones you try.

1. After a crawl: healthy, logged out, or broken?

The scraper ran. These five facts decide what happens next. The bottom AND gate is the one people forget: a scraper that used to find notices and now finds none is broken, even with no error.

logged_out_relogs If the portal refused the session, the verdict is always relogin.
silent_breakage_heals Not logged out, zero listings now, more than zero last time: always heal.
clean_is_healthy No crash, no invalid item, and listings found (or none ever expected): always healthy.
naive_misses_silent_breakage Remove the bottom AND gate and a portal redesign that returns nothing reads as healthy. Lean exhibits that exact case, so the gate is load-bearing.

2. The repair budget: when do we ask a person?

A broken or logged-out crawl spends one repair (a heal or a relogin), up to 3 in a row. After that the source waits for a person. One healthy crawl clears the count. Choose a verdict and press Next crawl to walk through it.

Next crawl's verdict:
heals_bounded The count never goes above 3, whatever the crawls do.
needsHuman_only_when_exhausted A person is asked only after 3 repairs, and never for a healthy crawl.
relogin_loop_reaches_human / naive_relogin_loops_forever A portal that refuses every fresh login reaches a person after 3 relogins. In the first draft relogins didn't spend the budget, and Lean showed that draft loops forever. This is the bug the model caught.

3. Ids from content: what changes which id?

Each id is the SHA-256 of its fields, each written as an 8-byte length and then the field's bytes. These are the real ids, computed in your browser with the same encoding as foundry/core/models.py. Edit a field and see which id changes.

opportunity_id source and portal id only
notice_id every field, with files as a sorted set

encode_injective Two different field lists never encode to the same bytes, so two ids can only match if SHA-256 itself collides. naive_collides: without the length header, ["ab","c"] and ["a","bc"] would collide.
opportunity_ignores_dynamic Edits to the title, due date, description, metadata or files never move the opportunity.
notice_same_iff Two scrapes share a notice id exactly when they have the same content. File order and repeated files don't count.

4. Storing a scraped notice: new, amended, or a repeat?

Rows are only ever inserted, never changed. Switch on whether the database already has this notice id and this opportunity id.

classify_unchanged_iff A repeat is exactly a notice id already stored. classify_amendment_iff An amendment is exactly a new notice id for a stored opportunity.
ingestAll_idempotent Running the same refresh twice adds nothing. ingestAll_order_free Scrape order doesn't matter. ingestAll_keeps A stored row is never dropped or rewritten.

5. The handoff: agent, person, and the clock (TLA+)

This part is concurrent, so it is model-checked with TLA+ instead of proved in Lean. TLC tried every ordering of these steps for 2 runs racing for one source and 2 helpers, with lapsed leases, worker stalls and clock skew between the server and the worker.
